Hotfix - Runtime crash in Home calculator (2026-03-13)
Issue reported
- `CalculatorComponent.vue:126 Uncaught TypeError: Cannot read properties of undefined (reading 'relationships')`
- Symptom: blank/partial page due unhandled template exception.

Root cause
- In Vuetify select slots, `item.raw` can be undefined during render transitions.
- Template accessed `item.raw.relationships` directly.

Fix applied
- File: src/views/Home/PricingCards/CalculatorComponent.vue
- Added safe extractor function `getRawCurrency(item)`.
- Replaced all direct `item.raw` dereferences with safe optional access.
- Added guarded click handler `selectCurrencyFromItem(item)`.

Post-fix validation
- npm run typecheck: SUCCESS
- npm run build: SUCCESS

Visual regression correction pass - 2026-03-14
Issue reported
- After Vuetify major upgrade, visual differences appeared (brand color drift, typography drift, low button text contrast).
- Most visible in Home and some Dashboard sections.

Root causes identified
- `primary` theme color in `src/plugins/vuetify.ts` was set to `#000000`, conflicting with project design token `$color-primary: #5043E8`.
- Vuetify components in v4 rely on `--v-font-family`; only body-level overrides were present.
- Some primary buttons could inherit non-contrast text color depending on utility classes.

Fixes applied (minimal, global-safe)
- `src/plugins/vuetify.ts`
  - `primary` restored to `#5043E8`.
  - Added explicit contrast tokens: `on-primary: #FFFFFF`, `on-secondary: #FFFFFF`.
  - Set `theme.defaultTheme = "light"` explicitly.

- `src/scss/_override.scss`
  - Added global Vuetify font variable:
    - `--v-font-family: ProximaNova, "DM Sans", sans-serif;`
  - Added contrast safeguard for primary buttons:
    - `.v-btn.bg-primary { color: rgb(var(--v-theme-on-primary)) !important; }`
  - Added explicit theme variable fallback:
    - `--v-theme-on-primary: 255, 255, 255;`

Validation executed
- npm run typecheck -> SUCCESS
- npm run build -> SUCCESS

Notes
- Fix scope intentionally limited to global theme/typography/contrast to avoid functional changes and preserve existing component structure.

Security enhancement - Wallet operations 2FA guard (2026-03-15)
Objective
- Require 2FA (only when enabled) for wallet/account mutations: create, edit, delete, restore.
- Keep login 2FA flow unchanged.
- Provide reusable helper to apply same guard in other modules.

Implementation
1) New reusable helper
- Added: src/composables/useTwoFactorGuard.ts
- Exposes:
  - hasTwoFactorEnabled()
  - runWithTwoFactor(action)
- Behavior:
  - If 2FA disabled -> executes action directly.
  - If 2FA enabled -> opens existing TwoFactor modal flow and executes action only after successful verification.

2) Hardened 2FA verification flow
- Updated: src/stores/TwoFactorAuthStore.ts (ejectFunction2)
- Before: modal closed even on invalid code/password in newFlow path.
- Now: verification request is awaited; callback executes only on success; modal remains active on failure (code cleared), preventing bypass.

3) Enabled guard only in wallet/account user CRUD screens
- Updated CRUD submit gate:
  - src/components/global/CrudComponent.vue
  - New optional prop: requireTwoFactor
  - Create/Edit operation wrapped with runWithTwoFactor when prop enabled.
- Updated delete/restore gate:
  - src/components/global/TableComponent.vue
  - New optional prop: requireTwoFactor
  - Delete/Restore operation wrapped with runWithTwoFactor when prop enabled.

4) Activated guard in user wallet/account views
- src/views/user/wallet/WalletView.vue
- src/views/user/Accounts/Bank/BankAccountView.vue
- src/views/user/Accounts/Efecty/EfectyAccountCompanyView.vue
- src/views/user/Accounts/Other/OtherAccountView.vue
- Added `requireTwoFactor` to both CrudComponent and TableComponent in those views.

Validation
- npm run typecheck: SUCCESS
- npm run build: SUCCESS

Notes
- No refactor of login 2FA flow.
- Changes are additive/minimal and reusable for future sensitive actions by setting `requireTwoFactor` or calling runWithTwoFactor directly.
